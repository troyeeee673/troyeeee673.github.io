# Linux内核中断

## 裸机中断处理方法

### 1. 整体流程

裸机中断处理分为三个核心步骤：

\1. *使能中断*：配置相关寄存器

\2. *注册中断服务函数*：填入中断向量表

\3. *中断分发*：在 IRQ 入口函数中查表执行

### 2. 具体步骤详解

#### （1）使能中断，初始化相关寄存器

- 使能****总中断开关****（如 ARM 的 CPSR 寄存器 I 位）

- 配置具体外设的****中断使能寄存器****

- 配置****中断控制器****（如 NVIC、GIC），设置优先级

#### （2）注册中断服务函数

- 维护一个****中断服务函数表****：irqTable[ ] 数组

- 向数组的****指定标号处****写入对应的中断服务函数指针

- 标号 = 中断号（由硬件或中断控制器定义）

#### （3）中断处理分发流程

- 中断发生 → CPU 跳转到****IRQ 中断服务函数入口****

- 在 IRQ 入口函数中：

- 保存现场（寄存器压栈）

- 读取中断控制器，获取当前发生的中断号

- 以中断号为索引，去 irqTable[ ] 数组中查找对应的处理函数

- 找到后跳转执行具体的中断处理

- 恢复现场（寄存器出栈）

- 返回被中断的代码

## 1.2 Linux 中断处理

### 1. 中断使用流程

Linux 内核中中断处理的四个核心步骤:

```

\1. 获取中断号

↓

\2. 申请中断（request_irq）

↓

\3. 实现中断处理函数

↓

\4. 释放中断（free_irq）

```

-–

### 2. 步骤详解

#### （1）获取中断号

在使用中断前，首先要知道设备对应的中断号。

| 场景 | 获取方式 | 示例 |

|——|———|——|

| *GPIO 中断* | gpio_to_irq(gpio_num) | irq = gpio_to_irq(18); |

| *设备树中断* | irq_of_parse_and_map() | irq = irq_of_parse_and_map(node, 0); |

| *平台设备* | platform_get_irq() | irq = platform_get_irq(pdev, 0); |

| *硬件固定* | 查芯片手册 | 如 UART 中断号、定时器中断号 |

-–

#### （2）申请中断（request_irq）

```c

#include <linux/interrupt.h>

int request_irq(unsigned int irq, // 中断号

​ irq_handler_t handler, // 中断处理函数

​ unsigned long flags, // 中断标志

​ const char *name, // 设备名称

​ void *dev_id); // 设备标识

```

*参数说明：*

| 参数 | 作用 | 说明 |

|——|——|——|

| irq | 中断号 | 通过第一步获取 |

| handler | 中断处理函数 | 发生中断时被回调 |

| flags | 中断触发方式/属性 | 见下方表格 |

| name | 设备名称 | 在 /proc/interrupts 中显示 |

| dev_id | 设备标识 | 用于共享中断时区分设备，通常传设备结构体指针 |

*常用标志（flags）：*

| 标志 | 说明 |

|——|——|

| IRQF_SHARED | 共享中断（多个设备共用同一中断号） |

| IRQF_TRIGGER_RISING | 上升沿触发 |

| IRQF_TRIGGER_FALLING | 下降沿触发 |

| IRQF_TRIGGER_HIGH | 高电平触发 |

| IRQF_TRIGGER_LOW | 低电平触发 |

| IRQF_ONESHOT | 顶半部执行完才重新使能中断 |

*返回值：*

- 0：申请成功

- -EINVAL：中断号无效或处理函数为 NULL

- -EBUSY：中断已被占用且不共享

> ⚠️ *注意*：request_irq() 会****自动使能/激活中断****，无需额外操作。

-–

#### （3）中断处理函数

*函数原型：*

```c

typedef irqreturn_t (*irq_handler_t)(int irq, void *dev_id);

irqreturn_t my_interrupt_handler(int irq, void *dev_id);

```

*参数说明：*

| 参数 | 说明 |

|——|——|

| irq | 触发的中断号（同一个函数可服务多个中断） |

| dev_id | 与 request_irq 中传入的 dev_id 一致，用于区分设备 |

*返回值：*

| 返回值 | 含义 |

|——–|——|

| IRQ_NONE | 该中断不是本设备产生的（用于共享中断判断） |

| IRQ_HANDLED | 中断已正确处理 |

| IRQ_WAKE_THREAD | 唤醒中断线程（用于 threaded_irq） |

*中断处理函数中的限制：*

- 在****原子上下文****中执行，不能睡眠

- 不能调用可能睡眠的函数（如 mutex_lock()、msleep()、copy_from_user() 等）

- 执行时间要尽量短

- 不能访问用户空间内存

-–

#### （4）释放中断（free_irq）

```c

void free_irq(unsigned int irq, void *dev_id);

```

*参数：*

| 参数 | 说明 |

|——|——|

| irq | 要释放的中断号 |

| dev_id | 必须与 request_irq 传入的 dev_id 一致 |

*作用：*

- 释放中断资源

- 如果存在共享中断，只移除对应的 dev_id

- 会等待正在执行的中断处理函数完成

> ⚠️ *注意*：模块卸载时必须释放已申请的中断，否则会导致系统不稳定。

### 4. 与裸机中断的对比

| 对比项 | 裸机中断 | Linux 中断 |

|——–|———|———–|

| *中断号获取* | 查手册固定值 | API 动态获取 |

| *中断注册* | 手动填写 irqTable[] 数组 | request_irq() 注册 |

| *中断使能* | 手动操作寄存器 | request_irq() 自动激活 |

| *中断释放* | 不需要 | free_irq() 释放资源 |

| *中断处理函数* | 无返回值 | 必须有返回值（IRQ_HANDLED/IRQ_NONE） |

-–

### 5. 调试命令

```bash

# 查看中断统计信息

cat /proc/interrupts

# 查看软中断统计

cat /proc/softirqs

```

-–

### 6. 关键要点总结

| 要点 | 说明 |

|——|——|

| *先获取中断号* | 不能直接写死，尤其是 GPIO 中断 |

| *request_irq 自动激活* | 不需要额外使能中断 |

| *必须释放中断* | 模块卸载时调用 free_irq() |

| *dev_id 要一致* | 申请和释放时传相同的指针 |

| *处理函数要快* | 不要在中断中做耗时操作 |

| *不能睡眠* | 中断处理函数中不能调用可能睡眠的函数 |

## Linux 中断底半部机制

### 为什么需要底半部？

中断处理原则：*中断处理越快越好*（顶半部执行时间要短）

| 机制 | 执行上下文 | 特点 |

|——|———–|——|

| *顶半部（硬中断）* | 原子上下文 | 快速响应，不能睡眠，执行耗时操作会阻塞系统 |

| *底半部* | 软中断/进程上下文 | 处理耗时的剩余工作，可被中断打断 |

### 1. 软中断（SoftIRQ）

#### （1）核心数据结构

```c

// 内核定义 10 个软中断

static struct softirq_action softirq_vec[NR_SOFTIRQS];

// 软中断类型枚举

enum {

HI_SOFTIRQ = 0, // 高优先级 tasklet

TIMER_SOFTIRQ, // 定时器软中断

NET_TX_SOFTIRQ, // 网络发送

NET_RX_SOFTIRQ, // 网络接收

BLOCK_SOFTIRQ, // 块设备

BLOCK_IOPOLL_SOFTIRQ,

TASKLET_SOFTIRQ, // 普通 tasklet

SCHED_SOFTIRQ, // 调度器

HRTIMER_SOFTIRQ, // 高精度定时器

RCU_SOFTIRQ, // RCU 锁

NR_SOFTIRQS = 10

};

```

#### （2）软中断使用流程

```

\1. 注册软中断 → open_softirq()

\2. 触发软中断 → raise_softirq()

\3. 内核在合适时机执行软中断处理函数

```

#### （3）API 函数

```c

#include <linux/interrupt.h>

// 注册软中断

void open_softirq(int nr, void (*action)(struct softirq_action *));

// 参数：nr = 软中断号（如 NET_RX_SOFTIRQ）

// action = 软中断处理函数

// 触发软中断

void raise_softirq(unsigned int nr);

// 参数：nr = 要触发的软中断号

```

#### （4）软中断特点

| 特点 | 说明 |

|——|——|

| *静态分配* | 编译时确定数量（10个），不能动态增加 |

| *全局性* | 所有 CPU 共享，需考虑并发 |

| *执行时机* | 硬件中断返回前、ksoftirqd 内核线程 |

| *可重入* | 同一软中断可在不同 CPU 同时执行 |

| *不能睡眠* | 在原子上下文中执行 |

> ⚠️ *驱动开发中一般不直接使用软中断*（太底层，并发复杂），而是使用更高级的 *tasklet*。

-–

### 2. Tasklet（基于软中断实现）

Tasklet 是****基于软中断实现的更高级封装****，驱动开发中最常用的底半部机制。

#### （1）Tasklet 工作原理

```

硬件中断发生

↓

顶半部（硬中断处理函数）

↓

调用 tasklet_schedule()

↓

将 tasklet 加入队列

↓

内核在 TASKLET_SOFTIRQ 软中断中执行

↓

tasklet 处理函数执行

```

#### （2）Tasklet 使用流程

```

\1. 定义 tasklet 结构体

\2. 初始化 tasklet（绑定处理函数）

\3. 在顶半部中调用 tasklet_schedule()

\4. 内核自动调度执行 tasklet 处理函数

```

#### （3）API 函数

```c

#include <linux/interrupt.h>

// 定义 tasklet 结构体

struct tasklet_struct {

struct tasklet_struct *next;

unsigned long state;

atomic_t count;

void (*func)(unsigned long data);

unsigned long data;

};

// 方式一：动态初始化（运行时）

void tasklet_init(struct tasklet_struct *t,

​ void (*func)(unsigned long data),

​ unsigned long data);

// 方式二：静态初始化（编译时）

#define DECLARE_TASKLET(name, func, data) \

struct tasklet_struct name = { … }

// 调度 tasklet（在顶半部中调用）

void tasklet_schedule(struct tasklet_struct *t);

// 禁止 tasklet 调度

void tasklet_disable(struct tasklet_struct *t);

void tasklet_disable_nosync(struct tasklet_struct *t);

// 使能 tasklet 调度

void tasklet_enable(struct tasklet_struct *t);

// 终止 tasklet（会等待执行完成）

void tasklet_kill(struct tasklet_struct *t);

```

### 3. Tasklet 特点总结

| 特点 | 说明 |

|——|——|

| *基于软中断* | 基于 TASKLET_SOFTIRQ 或 HI_SOFTIRQ 实现 |

| *串行执行* | 同一 tasklet 只能在一个 CPU 上执行，不会重入 |

| *不能睡眠* | 仍在软中断上下文（原子环境） |

| *适合中轻度工作* | 不能做太耗时的操作 |

| *驱动开发常用* | 比软中断更简单、安全 |

-–

### 4. 顶半部与底半部分工对比

| 对比项 | 顶半部（硬中断） | 底半部（Tasklet） |

|——–|—————-|——————|

| *响应速度* | 立即响应 | 延迟执行（内核调度） |

| *能否睡眠* | ❌ 不能 | ❌ 不能（软中断上下文） |

| *可中断* | 可被其他中断打断 | 可被中断打断 |

| *执行时间* | 必须非常短 | 可稍长，但不宜过久 |

| *主要工作* | 紧急响应、调度底半部 | 处理剩余工作 |

-–

### 5. 关键要点总结

| 要点 | 说明 |

|——|——|

| *软中断数量固定* | 10 个，驱动一般不用 |

| *tasklet 是软中断封装* | 基于 TASKLET_SOFTIRQ 实现 |

| *两步使用* | ①初始化（绑定函数）②在顶半部调用 tasklet_schedule() |

| *不能睡眠* | tasklet 仍运行在原子上下文 |

| *模块卸载要 tasklet_kill()* | 确保 tasklet 执行完毕 |

## 3. 工作队列（Workqueue）

### （1）为什么需要工作队列？

| 机制 | 能否睡眠 | 适用场景 |

|——|———|———-|

| 软中断 | ❌ 不能 | 高吞吐量、性能要求极高 |

| Tasklet | ❌ 不能 | 驱动常用的底半部，轻度工作 |

| *工作队列* | ✅ *可以睡眠* | *复杂、耗时、需要睡眠的操作* |

> 当底半部需要****大量计算、访问文件系统、等待信号量****等操作时，必须使用工作队列。

-–

### （2）工作队列原理

工作队列将底半部工作****交给内核线程****执行，因此：

- 运行在****进程上下文****，可以睡眠

- 可以被调度，不占用中断上下文时间

- 响应延迟稍大，但更安全

```

硬件中断发生

↓

顶半部（硬中断处理函数）— 快速响应

↓

调度工作队列（schedule_work / queue_work）

↓

内核工作线程（kworker）唤醒

↓

工作队列处理函数执行（进程上下文，可睡眠）

```

-–

### （3）工作队列核心 API

#### ① 共享工作队列（系统默认）

```c

#include <linux/workqueue.h>

// 定义工作结构体

struct work_struct my_work;

// 初始化工作（绑定处理函数）

INIT_WORK(&my_work, my_work_func);

// 调度工作（加入系统默认工作队列）

bool schedule_work(struct work_struct *work);

// 延时调度

bool schedule_delayed_work(struct delayed_work *dwork, unsigned long delay);

```

#### ② 自定义工作队列（独立线程）

```c

// 创建工作队列（返回指针）

struct workqueue_struct *create_workqueue(const char *name);

struct workqueue_struct *create_singlethread_workqueue(const char *name);

// 将工作放入自定义队列

bool queue_work(struct workqueue_struct *wq, struct work_struct *work);

// 延时放入

bool queue_delayed_work(struct workqueue_struct *wq,

​ struct delayed_work *dwork,

​ unsigned long delay);

// 销毁工作队列

void destroy_workqueue(struct workqueue_struct *wq);

```

-–

### （4）工作结构体类型

| 结构体 | 说明 | 初始化函数 |

|——–|——|———–|

| struct work_struct | 普通工作 | INIT_WORK() |

| struct delayed_work | 延时工作 | INIT_DELAYED_WORK() |

*工作处理函数原型：*

```c

// 普通工作函数

void my_work_func(struct work_struct *work);

// 延时工作函数（同样原型）

void my_delayed_work_func(struct work_struct *work);

```

### （6）延时工作队列示例

```c

#include <linux/module.h>

#include <linux/workqueue.h>

static struct delayed_work my_delayed_work;

// 延时工作处理函数

static void my_delayed_work_func(struct work_struct *work)

{

printk(KERN_INFO “Delayed work executed after 1 second\n”);

}

static int __init test_init(void)

{

// 初始化延时工作

INIT_DELAYED_WORK(&my_delayed_work, my_delayed_work_func);

// 1秒后执行

schedule_delayed_work(&my_delayed_work, msecs_to_jiffies(1000));

return 0;

}

static void __exit test_exit(void)

{

// 取消延时工作

cancel_delayed_work(&my_delayed_work);

}

module_init(test_init);

module_exit(test_exit);

MODULE_LICENSE(“GPL”);

```

-–

### （7）自定义工作队列示例

```c

// 定义独立工作队列

static struct workqueue_struct *my_wq;

static struct work_struct my_custom_work;

static void my_custom_work_func(struct work_struct *work)

{

printk(KERN_INFO “Custom workqueue executed\n”);

}

static int __init test_init(void)

{

// 1. 创建工作队列（独立内核线程）

my_wq = create_workqueue(“my_wq”);

if (!my_wq) {

​ printk(KERN_ERR “create_workqueue failed\n”);

​ return -ENOMEM;

}

// 2. 初始化工作

INIT_WORK(&my_custom_work, my_custom_work_func);

// 3. 放入自定义队列

queue_work(my_wq, &my_custom_work);

return 0;

}

static void __exit test_exit(void)

{

// 确保工作完成

flush_workqueue(my_wq);

// 销毁工作队列

destroy_workqueue(my_wq);

}

module_init(test_init);

module_exit(test_exit);

MODULE_LICENSE(“GPL”);

```

-–

### （8）三种底半部机制对比总结

| 对比项 | 软中断 | Tasklet | 工作队列 |

|——–|——–|———|———-|

| *执行上下文* | 原子上下文 | 原子上下文 | *进程上下文* |

| *能否睡眠* | ❌ 不能 | ❌ 不能 | ✅ *可以* |

| *响应延迟* | 最低 | 较低 | 较高 |

| *并发性* | 全局，需考虑并发 | 串行，不会重入 | 可配置 |

| *使用复杂度* | 复杂 | 简单 | 中等 |

| *适用场景* | 高性能网络/块设备 | 驱动通用底半部 | *复杂、耗时任务* |

| *驱动开发常用* | ❌ 少用 | ✅ 常用 | ✅ 常用 |

-–

### （9）关键要点总结

| 要点 | 说明 |

|——|——|

| *工作队列 = 内核线程* | 工作在进程上下文，可以睡眠 |

| *两种使用方式* | 系统默认队列（schedule_work）或自定义队列（queue_work） |

| *适用场景* | 需要睡眠、耗时、复杂的底半部工作 |

| *延时工作* | 使用 schedule_delayed_work() 可实现延时执行 |

| *模块卸载* | 需调用 flush_work() 或 flush_workqueue() 确保工作完成 |

| *自定义队列* | 可创建独立工作队列避免影响系统性能 |

-–

### （10）三种机制选择建议

```

中断发生 → 需要底半部处理

│

├── 工作非常轻量、快速 → 直接在顶半部处理

│

├── 需要睡眠、访问文件系统、耗时 → 使用工作队列

│

├── 不需要睡眠，但有一定工作量 → 使用 Tasklet

│

└── 性能要求极高（网络/块设备） → 使用软中断

```

## 1.4 设备树中断节点信息

### 1. 中断节点三大核心属性

| 属性 | 作用 | 说明 |

|——|——|——|

| interrupt-controller | 声明该节点为中断控制器 | 空属性，表示当前节点是一个中断控制器 |

| #interrupt-cells | 指定 interrupts 属性中 cell 的数量 | 告诉设备树如何解析中断信息 |

| interrupt-parent | 指定父中断控制器 | 设备引用哪个中断控制器，可向上继承 |

-–

### 2. 中断控制器节点详解（以 GIC 为例）

```dts

intc: interrupt-controller@00a01000 {

compatible = “arm,cortex-a7-gic”;

#interrupt-cells = <3>; // 每个中断用3个cell描述

interrupt-controller; // 声明为中断控制器

reg = <0x00a01000 0x1000>,

​ <0x00a02000 0x100>;

};

```

*#interrupt-cells = <3>* 含义：**

每个 interrupts 需要 3 个 cell：

```dts

interrupts = <中断类型 中断号 触发方式>;

```

| Cell | 说明 | 常见值 |

|——|——|——–|

| 第1个 | 中断类型（SPI/PPI/SGI） | GIC_SPI(0)、GIC_PPI(1) |

| 第2个 | 中断号 | 如 74、75 |

| 第3个 | 触发方式 | IRQ_TYPE_LEVEL_HIGH、IRQ_TYPE_EDGE_RISING |

-–

### 3. GPIO 中断控制器节点详解

```dts

gpio5: gpio@020ac000 {

compatible = “fsl,imx6ul-gpio”, “fsl,imx35-gpio”;

reg = <0x020ac000 0x4000>;

interrupts = <GIC_SPI 74 IRQ_TYPE_LEVEL_HIGH>,

​ <GIC_SPI 75 IRQ_TYPE_LEVEL_HIGH>;

gpio-controller; // 声明为GPIO控制器

interrupt-controller; // 声明为中断控制器

};

```

*GPIO 中断的 #interrupt-cells = <2> 含义：*

```dts

interrupts = <GPIO编号 触发方式>;

```

| Cell | 说明 | 示例 |

|——|——|——|

| 第1个 | GPIO 引脚编号 | 0、1、2…（对应 GPIO5_IO00、GPIO5_IO01…） |

| 第2个 | 触发方式 | 见下方表格 |

### 4. 设备中断节点详解（以 FXLS8471 为例）

```dts

fxls8471@1e {

compatible = “fsl,fxls8471”;

reg = <0x1e>;

position = <0>;

interrupt-parent = <&gpio5>; // 指定父中断控制器为 gpio5

interrupts = <0 8>; // 使用 GPIO5_IO00，低电平有效

};

```

*解析过程：*

```

interrupt-parent = <&gpio5>

→ 查找 gpio5 节点的 #interrupt-cells = <2>

→ 知道 interrupts 有 2 个 cell

interrupts = <0 8>

→ cell 0 = GPIO 编号 = 0（即 GPIO5_IO00）

→ cell 1 = 触发方式 = 8（低电平有效）

```

-–

### 5. 触发方式编码表（第2个 cell）

| 值 | 触发方式 | 宏定义 | 说明 |

|—-|———|——–|——|

| 0 | 无触发 | - | 不使用中断 |

| 1 | 上升沿触发 | IRQ_TYPE_EDGE_RISING | low-to-high edge triggered |

| 2 | 下降沿触发 | IRQ_TYPE_EDGE_FALLING | high-to-low edge triggered |

| 3 | 双边沿触发 | IRQ_TYPE_EDGE_BOTH | both edges |

| 4 | 高电平触发 | IRQ_TYPE_LEVEL_HIGH | active high level-sensitive |

| 8 | 低电平触发 | IRQ_TYPE_LEVEL_LOW | active low level-sensitive |

> ⚠️ *注意*：不同中断控制器可能使用不同的编码，如 GIC 使用独立宏定义（IRQ_TYPE_LEVEL_HIGH 等），GPIO 中断控制器则直接使用数字编号。具体值要参考对应控制器的绑定文档。

-–

### 6. 完整解析流程

```

设备节点 fxls8471

│

├── interrupt-parent = <&gpio5>

│ ↓

│ 查找 gpio5 节点

│ ↓

│ gpio5.#interrupt-cells = <2>

│ ↓

│ 说明 interrupts 有 2 个 cell

│

└── interrupts = <0 8>

​ ↓

​ cell 0 = 0 → GPIO5_IO00

​ cell 1 = 8 → 低电平有效

​ ↓

​ 最终中断信息：GPIO5_IO00, 低电平触发

```

### 7. 关键要点总结

| 要点 | 说明 |

|——|——|

| *interrupt-controller******* | 空属性，标记该节点为中断控制器 |

| *#interrupt-cells******* | 指定子节点 interrupts 属性中 cell 的数量 |

| *interrupt-parent******* | 指定设备使用哪个中断控制器（默认继承父节点） |

| *interrupts******* | 具体的终端描述，cell 数量由 #interrupt-cells 决定 |

| *GPIO 转中断* | GPIO 控制器的 interrupts 描述其自身连接到 GIC 的中断，子设备的 interrupts 描述 GPIO 引脚号和触发方式 |

### 8. 驱动中获取中断号

```c

// 设备树节点中获取中断号

struct device_node *np = pdev->dev.of_node;

int irq_num;

// 方式一：直接获取

irq_num = irq_of_parse_and_map(np, 0); // 获取第0个中断

// 方式二：platform 方式获取

irq_num = platform_get_irq(pdev, 0);

// 方式三：GPIO 方式获取（如果知道 GPIO 编号）

int gpio = of_get_gpio(np, 0);

irq_num = gpio_to_irq(gpio);

```
