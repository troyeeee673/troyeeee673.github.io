IMX6ULL 的 I²C 通信与 AP3216C 环境光传感器实践

I²C 是嵌入式开发中最常用的总线之一。本文以 ALPHA 开发板上的 AP3216C 环境光传感器为例，从 I²C 协议本身出发，再到 IMX6ULL 的 I²C 控制器配置，最后补充一个实际编程中容易踩的坑，形成一个完整的驱动开发记录。

一、I²C 协议

1.1 硬件基础

I²C 总线只需要两根线：SCL（串行时钟）和 SDA（串行数据）。这两条线必须通过上拉电阻拉到 VCC（通常是 4.7KΩ 拉到 3.3V），以保证总线空闲时电平稳定。一条 I²C 总线上可以挂载多个从机，通信时通过从机地址来区分目标设备。

在 ALPHA 开发板上，AP3216C 连接到了 I2C1 接口，引脚复用情况如下：

I²C 信号 功能 IMX6ULL 引脚 复用模式
SCL 串行时钟 UART4_TXD ALT2
SDA 串行数据 UART4_RXD ALT2

1.2 一次完整的数据读取流程

I²C 通信以 START 信号开始，以 STOP 信号结束。以从 AP3216C 的某个寄存器读取数据为例，完整的过程可拆解为以下步骤：

  1. 主机发送起始信号（START），占据总线。
  2. 主机发送从设备地址 + 写控制位，告诉总线要和谁通信、接下来要做什么。
  3. 从机回应一个 ACK 应答信号，表示“我在，收到”。
  4. 主机发送目标寄存器地址，告诉从机要读哪个位置的数据。
  5. 从机再次回应 ACK。
  6. 主机再次发送起始信号（Repeated START）。
  7. 主机再次发送从设备地址 + 读控制位，切换为读模式。
  8. 从机回应 ACK。
  9. 从机将目标寄存器的数据发送到总线上。
  10. 主机收到数据后，发出 NO ACK 信号，表示“读取完成，不用再发了”。
  11. 主机发送停止信号（STOP），释放总线。

可以看出，I²C 读操作的精髓在于先写后读——先通过“写”动作告诉从机想读的寄存器地址，再通过“读”动作获取数据。

二、IMX6ULL I²C 控制器核心配置

IMX6ULL 的 I²C 外设支持标准模式（100kbit/s）和快速模式（400kbit/s），开发时主要涉及以下几个关键寄存器。

2.1 时钟与波特率

  • 时钟源：I²C 模块的根时钟来自 perclk_clk_root，也就是 ipg_clk_root，频率为 66MHz。
  • 分频设置：通过 IFDR 寄存器的低 6 位设置分频系数。以 100kbit/s 的目标速率为例，计算过程如下：
    • 所需分频值 = 66000000 / 100000 = 660。
    • 查阅参考手册，当 IFDR 设为 0x38 或 0x15 时，对应 640 分频。
    • 实际速率 = 66000000 / 640 ≈ 103.125kbit/s，误差在可接受范围内。

2.2 控制与状态寄存器

  • I2CR（控制寄存器）：
    • bit7：I²C 使能位，置 1 开启模块。
    • bit5：主从模式选择，置 1 为主机模式。
    • bit4：收发控制，置 1 为发送，置 0 为接收。
  • I2SR（状态寄存器）：
    • bit7：传输完成标志，1 表示本次传输已完成。
    • bit5：总线忙闲标志，0 表示空闲，1 表示忙。
    • bit0：ACK 接收位，用于判断从机是否应答。
  • I2DR（数据寄存器）：收发数据的直接窗口，要发送的数据写入这里，接收到的数据也从这里读出。

三、实际编程中的一个坑：浮点运算卡死

在调试过程中，我遇到一个容易忽视的问题：程序一运行到浮点计算就直接卡死。

问题原因

IMX6ULL 内部集成了硬件浮点运算单元（FPU），但在裸机或某些轻量级 RTOS 环境下，需要手动开启，并在编译时正确指定浮点 ABI，否则处理器执行到浮点指令会触发未定义指令异常。

解决方法

两步走：

  1. 硬件层面：在启动代码中，确保 CPACR（协处理器访问控制寄存器）的 CP10 和 CP11 位已置 1，使能 FPU。
  2. 编译层面：在 Makefile 或 IDE 的编译选项中，添加硬件浮点支持，例如 -mfloat-abi=hard。

做完这两步后，浮点运算便恢复正常。
